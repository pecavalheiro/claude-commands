# Fast requirements run: the rules

One file, read top to bottom once at the start of the run, and again after a resume or a context compaction. This file IS the run: nothing in it is applied from memory of an earlier run, fast or full.

The run is one context. You read the sources, you read the code, you ask the questions, you write the spec. Subagents are the exception, not the method: at most 3 in a run, each for one of the three cases named in section 7, each with a 40-tool-call ceiling. The full command fans out dozens of agents and verifies every claim; a fast run spends its tokens on the ticket's own neighbourhood and verifies what the spec rests on. Deep thinking is for decisions, not for every step.

Ceilings for the whole run, each a number to stay under and to report in the phase notes: 25 fetched sources, 40 code reads before the first question, 3 agents, 5 questions per round, `research-notes.md` under 15KB, a spec sized to the change.

## 0. Setup

Runs live in `~/.claude/runs/`, never in the repo. `<repo>` is `basename -s .git "$(git remote get-url origin)"`; no `origin` → the only remote's basename; no remotes → the basename of `git rev-parse --show-toplevel`; an empty key or no git repository → stop ("not inside a git repository: the run store is keyed by repo"). `<workspace>` is `git rev-parse --show-toplevel`; its slug is that path with `/` replaced by `-`. Create `~/.claude/runs/<repo>/requirements/YYYY-MM-DD-HHMM-<TICKET-ID>-[slug]/` (`mkdir -p`; no ticket → no ticket segment), write `00-initial-request.md` (the request verbatim + a summary of the primary source), `metadata.json` (below), an empty `gates.md`, and the pointer `~/.claude/runs/<repo>/requirements/.pointers/<workspace-slug>` (two lines: run-folder name, raw workspace path). Print a ready-to-type `/rename <TICKET-ID>-[slug]` once and move on. Never scan, read or search other run folders; a prior document enters only if I name its path, and then as a source to quote, never as decisions.

```json
{ "id": "feature-slug", "mode": "fast", "workspace": "/abs/path", "worktree": { "path": "/abs/path", "branch": "name", "createdAtStart": true },
  "started": "ISO-8601", "lastUpdated": "ISO-8601", "status": "active | complete | incomplete", "phase": "discovery|context|detail|verification|complete",
  "progress": { "discovery": { "answered": 0, "total": 0 }, "detail": { "answered": 0, "total": 0 } },
  "contextFiles": [], "relatedFeatures": [], "sources": { "linear": [], "notion": [], "slack": [], "gitlab": [] },
  "verification": { "lastRun": null, "originSha": null, "codeClaimsChecked": 0, "quotesChecked": 0, "unverified": 0 }, "holds": [] }
```

`worktree` only when the router's Step 0 created one (omit otherwise). `holds` entries: `{ "comm": "C-3", "owner": "<team> (@who)", "askedAt": "ISO-8601", "heldFRs": ["FR-4"], "resolution": null | "answered" | "interim" | "descoped:<ticket>" }`. `status` and `phase` are never "complete" while a hold has `resolution: null`.

## 1. Sources: read them yourself

**Ring 0** is the ticket: description, every comment, attachments, relations. **Ring 1** is what ring 0 points at: links in the description and comments, the parent, tickets it blocks or depends on, the project or milestone page (the page, never its issue list), and any source I named. Fetch rings 0 and 1 completely with the native connectors: threads to the last reply, pages with their inline comments, an MR with its notes and diff. A linked channel is the threads the link points at or its last 30 messages, never its history. **Ring 2** is what ring-1 sources point at: open a ring-2 link only when its title or the linking sentence bears on a decision this ticket must make, and write one line why; everything else is listed as `skipped-by-title` (title, link, half-line reason). No ring 3. Ceiling 25 fetches; when rings 0 and 1 alone exceed it, fetch in this order until the ceiling (description links, parent and blocking relations, comment links, other relations) and list the rest.

**Search** is two or three queries you run yourself: the ticket id, and one or two terms distinctive to this feature, in the chat tool and the tracker. Open at most 5 hits whose title or snippet names this ticket's subject; list the others. Search for a person only when a source poses an open question to that person and no reply is linked.

**A connector or source that fails** does not stop you. Record it with what failed, where it is linked from, your criticality call (low, medium, high) and the textual coverage that substitutes for it. Low items are skipped and listed. Medium and high items are put to me once, together, when the reading is done (fix access / skip / abort), along with any temporary-key request from the third-party check below. A WebFetch that returns a login page is a failed fetch.

**Third-party API claims are never trusted from a ticket.** Verify endpoints, fields, hosts and auth the ticket or a ring-1 source asserts against the current official docs now; your training memory of a fast-moving API is a hypothesis, not a finding.

**Bulk reader, the first allowed agent.** When rings 0 and 1 together exceed about ten pages of text (roughly 40KB), hand the reading to one fresh agent so the raw text does not sit in your context for the rest of the run: it fetches the named sources only, writes verbatim quotes with locators to an evidence file progressively, and returns a compact list of claim candidates (one-line quote + locator) and the links it saw with their titles, at most about 150 lines. Otherwise read directly.

## 2. What you write down

`research-notes.md` holds, in this order: the sources read (one line each: what, how fetched, status); the claims register; the decision table (section 4); the currency snapshot; one line per agent launched. Target under 15KB in total.

A **claim** is a verbatim quote with a stable locator (permalink, block or page URL + heading, ticket URL + section, MR URL, file:line@sha) and a provenance tag: `[stated]` (the source says it), `[inferred]` (you derived it; list what it rests on), `[absent]` (no source addresses it; questions and autonomous decisions are made of these). Give a claim an ID (`LIN-<ticket>-N`, `SLK-N`, `PRD-N`, `MR-N`, `CODE-N`) **only when a question, a decision row, or an FR will cite it.** Everything else you read stays read, not registered. Record author and date when a question or draft will attribute the statement to someone: a message is credited to its writer, never to whoever agreed, and a bare "yes" confirms exactly the sentence it replies to. Open questions a source poses without a recorded decision are claims; so is anything you yourself propose, tagged `[model proposal, no source]`.

**Currency snapshot**, taken once the sources are read: the ticket's title, acceptance criteria and `updatedAt`; the state of every ring-1 ticket and MR; `git fetch origin` and the SHA of `origin/<default-branch>`. Read-only: `fetch`, `rev-parse`, `log`, `diff`, `show`; nothing moves a branch.

## 3. Code: read it yourself

Before the first question, at most 40 tool calls: the files the ticket and its ring-1 sources name, their callers and readers one level out (`git grep`), and one existing feature of the same kind for the house pattern. Read at the fetched SHA (`git show <sha>:<path>`, `git grep <pattern> <sha> -- <paths>`), never at a local branch's HEAD. After the discovery answers, read what the answers select: exact files to change, the precedent to copy, integration points in both directions (what the change writes, and every surface that reads or exposes it), constraints. Write `03-context-findings.md` as the implementer's brief: where to change what, which precedent to copy, which readers to keep working, each with file:line@sha. Not the search that found it.

**Evidence bars.** Static facts (names, enum values, schema fields, config): the defining file, file:line. Behavioral facts (side effects, transactions, retries, permission checks, schedules): the code that defines the behavior, never a call site alone; libraries get overridden. Absence ("no other callers", "no such column"): the exact search run (patterns, scope) and the SHA, or no claim; an absence in our code bounds what we built and never says what an external system can do. Literal values (countries, hosts, strings): resolved from the authoritative seed or config, never from memory. Anything short of its bar is written `[unverified]` with the hedge kept.

**Door-closing claims.** A claim that a capability the sources asked for cannot be delivered, or that cites net-new work as the reason to drop it, is the most dangerous claim in a run. It may never rest on an absence in our own code, and a claim about an external system's capability is never inferred from our client's limits. Before any such claim reaches a question or the spec, one fresh agent (the second allowed agent) is handed the goal, never your framed claim ("find a way to do X with existing code or the live API"), and tries to refute it with the adjacent primitive or the current docs, one verdict per limb. Unrefuted but unconfirmed is `[unverified]`, never "infeasible".

## 4. Questions: two rounds, five each at most

**Open each round with one message**: the sources read by system, the `skipped-by-title` list, the inaccessible list with my rulings inline, the search queries run, and the ask "Is there any thread, document or conversation relevant to this work that none of this reached, or anything in the skipped list I should open?" Wait. If I name a source, read it under the ring-1 rules, say what changed in one line, and continue. In the second round, only new sources since the first are listed, and the ask is repeated only if there are any. After a resume, re-present this message only if the previous one was never answered.

**Disposition before questions.** Every decision the spec must bake in (each `[absent]` item, each open question a source poses, each model proposal) gets a row in the decision table: decision → disposition → citation.
- *Source-settled*: an explicit decision from someone with authority over it; quote it; asking me is forbidden. A proposal, a lean, a non-owner's reply, or code ("what happens today") never settles "what should happen"; two conflicting sources are never an answer, precedence (current ticket or approved PRD > sketch or comment > superseded doc) only picks the recommended default.
- *Critical*, always asked, whatever else is true: a source poses it as open and nothing later settles it; live sources conflict about what THIS feature should do; its default is expensive to reverse (schema, data written under it, contracts other tickets build on) or produces new user- or externally-visible effects today's process does not (state writes, notifications, events, who gets processed); or its default takes a new compliance, legal or product-policy position. Dropping a capability a source asked for because you could not confirm it is always critical, stated as unconfirmed, never impossible. Whether something blocks me is my call. When a third party owns the final answer: name who and where, write a paste-ready draft under `~/.claude/requirements-phases/drafts-contract.md` (read it first), state the consequence if their answer differs (which FRs change), and offer exactly (a) I send the draft now and hold or descope the FR, (b) I set the interim, (c) I accept your recommended interim. Under (b) or (c) the spec records the decision as final with the interim provenance tag `phase-5-output.md` defines, and `communications.md` carries the ask.
- *Low-stakes third-party*: reversible, fail-safe (degrades to today's behaviour), not source-posed → `communications.md` with a recommended default and the consequence if the answer differs. Justified by low stakes, never by "not blocking".
- *Engineering*: which function, path or pattern → decide from house patterns, record the reason.
A model proposal never rides inside another question's option; it gets its own row, and if it is externally visible, its own question.

**Write every surviving question to the file before asking the first** (`01-discovery-questions.md`, then `04-detail-questions.md`). Each is yes/no (critical third-party items use the (a)/(b)/(c) form), carries a default with its citation, and an Evidence block: claim ID → one- or two-sentence verbatim quote → locator. No number, quote or behavioral statement without a claim ID. Before asking, check your own file against five things: a fact with no ID; an ID with no register row; a quote that does not say what the sentence says (above all a quote about one field or population generalized to another); a name that is not the register's author; an option that smuggles in something no source asked for. Fix, then ask one at a time, printing the Evidence block first. Zero questions is a good outcome when the decision table is complete. Record answers in `02-discovery-answers.md` / `05-detail-answers.md` only after the round. A decision I made is never re-asked, reworded or confirmed; if later reading changes its premise, present the changed premise once with the evidence and a new default.

The second round comes after the targeted code reading; its questions arise from what that reading established and are phrased for a product manager.

## 5. Verification: one agent, on the spec

Draft `06-requirements-spec.md` and `communications.md` (section 6). Then launch the third allowed agent, fresh, with the spec, the register section of `research-notes.md` and the claim IDs the FRs cite, never your reasoning. After `git fetch origin`, at the current `origin/<default-branch>` SHA it re-derives every `CODE-*` claim an FR, TR or AC cites, reading the whole current body of the function or module rather than the cited lines and re-running every absence search; it re-fetches up to ten cited source quotes, the ones under a user decision or a draft first, and checks quote, locator and author; and it reports any statement in the spec with no claim ID, any ID with no register row, and any `[unverified]` content stated as fact. Forty tool calls; one report file.

You then: correct every failed claim everywhere it appears (grep the working files); quarantine what could not be verified as `[unverified]` with the one fact that would settle it, and keep it out of the FRs (an Assumption at most); list the commits between the snapshot SHA and the current one that touch any cited path and read each for impact; re-fetch the ticket and diff its title and acceptance criteria against the snapshot; if any answer I gave rests on a premise that changed, present it once. Write the verification line into `research-notes.md` and `metadata.json`: `code claims checked <N>, <X> changed; quotes checked <M>, <Y> corrected; unverified <U>; origin <snapshot sha> → <sha>`.

## 6. The spec and the communications file

`06-requirements-spec.md` has exactly the section headings `~/.claude/requirements-phases/phase-5-output.md` defines, which /synthesize parses: Problem Statement, Solution Overview, Functional Requirements (FR-numbered), Technical Requirements, Implementation Hints, Acceptance Criteria, Assumptions, Out of Scope. Numbered headings are fine; the names are not negotiable.

**Sized to the change.** An FR exists for behaviour that changes or that I decided; unchanged behaviour is not an FR, and a mechanism nobody asked about is not an FR. Each FR states one final decision and carries one provenance tag: source-stated (claim IDs), user-decided (which answer), the interim tag, or engineering (one-line reason). No FR rests on an `[unverified]` claim. Prerequisites (flags, migrations, keys, config) are Technical Requirements rows. Acceptance criteria: one for the happy path and one for the failure path of each FR, in terms an implementer can turn into a test; more only where the FR touches a trigger, a background job, a retry or an external call, where timing, redelivery and the flag-off case need their own criterion. When a rule is replaced, include a case only the new rule passes. Assumptions name the fact that would settle each. Out of Scope lists what the sources asked for and this spec does not do, with the ticket or communications item that owns it. Banned anywhere in the file: revision narration, either/or options, people-coordination content ("confirm with", "pending", "FYI"), open questions. Before writing the acceptance criteria, read `~/.claude/journals/requirements-lessons.md` once if it exists (say how many lessons it holds, or that it is absent) and apply the lessons that match this spec.

`communications.md`, headed "NOT part of the spec; NOT input for /synthesize": every people-facing item with destination, recipient, paste-ready text under the drafts contract, the default that stands if unanswered, and the consequence if the answer differs. Echo the list in chat.

**Completion.** Set `status` and `phase` to "complete" (never with an open hold). Announce: the communications items, every interim decision, every Assumption, every source skipped or inaccessible, and close with "requirements gathering is COMPLETE", the worktree or workspace path, and the paste-ready `/synthesize <worktree name>`.

## 7. Phase notes, agents, resume

After each of the five phases (sources, code, discovery questions, targeted context + detail questions, spec), append three lines to `gates.md`: `## <phase> (<date -u>)`, what it produced as numbers (sources read / skipped / inaccessible; code reads; claims; decision rows; questions asked; FRs and ACs; verification line), and `budget: fetches <n> of 25, agents <n> of 3, research-notes <n>KB`. No pasted commands. `gates.md` is the resume pointer: after an interruption, read it, then this file, then continue.

**Agents.** Three cases only: the bulk reader (section 1), the refuter (section 3), the verifier (section 5). Every brief names its inputs exhaustively, states the 40-call ceiling, asks for progressive file writes and a compact return, and never says "find everything about X". Write one line per launch in `research-notes.md`. Before using a result, know the agent finished: its notification is in the conversation, or `ListAgents` shows it stopped and its file exists; never build on a result that has not arrived. A dead agent is relaunched once with the same brief; tell me if it dies twice. A turn ends into a question awaiting my answer, a running agent's notification, or the announced completion; otherwise keep working.

**Thinking.** Think when a decision needs it: dispositioning a critical item, judging a door-closing claim, sizing the spec. Do not deliberate over fetches, file writes, or counts.
