# Investigate Retro

Post-mortem on a `/investigate-ticket` case after the thread has moved on: a claim of mine was corrected, the vendor answered, the customer confirmed or denied, the real cause surfaced, or I rewrote the draft heavily before posting it. Input: the Slack thread that was investigated, or the ID of the `/investigate-ticket` session (see The session transcript below), plus what turned out to be wrong (my description, the later thread messages, a ticket or MR that fixed the bug). Sources for the findings, strongest first: the session transcript when I give an ID; this session's context when the investigation just ran here; findings I paste; and last a reconstruction from what I actually posted in the thread (resolve my Slack identity through the connector, and ask when ambiguous). A reconstruction is weaker than the findings, because posted text drops the evidence labels. Say which source you are working from.

A retro's job is to make future investigations better, not to make the journal longer. Every entry is paid for on every future case (`/investigate-ticket` loads the journal in full at Step 0 and walks it again in its audit), and most misses are not missing rules: they are existing rules in the command that did not bite. Default to tightening what exists over adding something new.

**This command writes nothing on its own.** No journal entry, no environment or domain fact, no command edit, not even a first journal file. The retro reports findings; I decide which ones get written. Each finding names its proposed fix (target file and the gist). The exact wording is shown when I pick the item, and written only after my explicit go-ahead for that item.

## The journal

`~/.claude/journals/investigation-lessons.md`: all projects, machine-local, in no repo. When it is missing, the first approved entry creates it. When the file exists, Read it first; the house style is defined by what is there. One lesson = trigger ("when …") + action ("do / check …") + an evidence tail (thread link and retro date, one or two lines, not a story). Sections mirror the steps of `/investigate-ticket` (thread, code, warehouse, telemetry, boundary, cross-check, audit, drafts) so a lesson lands next to the rule it sharpens. Merge at ENTRY level, by root cause: an entry sharing a new lesson's root cause is extended with a new evidence tail and a generalized action, never given a sibling bullet; a new entry needs a new mechanism. If the file would pass ~20 entries, propose consolidating same-root-cause entries as a finding of its own.

Two other journals receive facts, not method: `~/.claude/journals/investigation.md` (the environment file: tools, data surfaces, vendor boundaries, patterns that paid off) and `~/.claude/journals/domain.md` (domain facts). I maintain both by hand, so the retro never appends to them on its own: it shows the exact bullet and the section it belongs in, in that file's house style, and writes it only on my approval.

## The session transcript

When the argument is a session ID (a UUID, as shown by `claude --resume` and on every line of `~/.claude/history.jsonl`), the investigation's own record is on disk and is the primary source. Claude Code keeps one JSONL transcript per session under `~/.claude/projects/<folder>/<session-id>.jsonl`, where the folder is derived from the directory the investigation ran in, so locate it across every folder: `ls ~/.claude/projects/*/<session-id>.jsonl`. A unique prefix that resolves to exactly one file is accepted; several matches or none means asking me, not guessing. One record per line, in time order, each with a `timestamp`. Extract:

- **The thread.** The first `user` record is the command invocation, with the link inside `<command-args>…</command-args>`. Empty means ask.
- **The findings and every draft revision**, in order: `jq -r 'select(.type=="assistant") | .message.content[]? | select(.type=="text") | .text' <file>`. Thinking and tool records are skipped; the prose is the record, and it usually carries the findings, each draft, and the corrections between them.
- **My turns** (corrections, decisions, what I cut before posting): `jq -r 'select(.type=="user" and .isMeta != true) | .message.content | if type=="string" then . else (.[]? | select(.type=="text") | .text) end' <file>`, then drop lines starting with `<` (command tags and system reminders). The `isMeta` record is the expanded command text, not me; tool results are arrays without text blocks and fall out on their own.

The format is Claude Code's own and undocumented. If the filters return nothing, say so and fall back to the next source rather than inferring; if the transcript looks truncated or compacted, say that too. Transcripts hold private data (names, identifiers, payloads): nothing from them goes anywhere but this conversation and, for items I approve, the journals.

## Steps

1. Re-read the FULL thread to its end, including every reply that arrived after my last message, and any linked follow-up (a ticket, an MR, a second thread). Then read the CURRENT `~/.claude/commands/investigate-ticket.md` and the FULL lessons journal. You cannot classify a miss as a gap without knowing what the rulebook already says, and a "new lesson" that restates an existing rule is the retro failing its own purpose.
2. Reconstruct three things and keep them apart: what the investigation concluded (the findings, claim by claim, each with its evidence class, taken from the transcript when there is one), what I actually posted (the thread holds only that, and the difference between the draft and the posted text is revealed preference about register and judgment), and what turned out to be true (the later thread, the fix, the vendor's answer, the customer's confirmation).
3. **Verify the counter-claims like any claim.** "It was wrong" is itself a set of claims. Confirm each against the code and, through the same read-only connectors the investigation used, against production, before treating it as ground truth: a colleague's correction, a bot's answer, and a vendor's reply are all leads. Some challenges are mistaken; when one is, say so plainly, with evidence. A challenge can also be right in its facts and wrong in its premise; separate the two. Vendor systems stay READ-ONLY, and nothing is posted or executed by this command.
4. Classify every substantive claim of the deliverable (and, in answer mode, every question) as one of:
   - **held**: later evidence agrees, or the challenge did not survive step 3.
   - **missed-evidence**: an available source was not consulted, or not fully: the negative query, the affected user's own request log, the positive twin, the recurrence count, a second point in time, a fallback surface, the end of the thread.
   - **wrong-evidence**: the source was consulted but the claim did not follow from it: a true count attached to a false characterization, an inference carrying an observation's confidence, proof implied beyond actual access, an assertion about an external system made from our side alone, a UI noun never verified.
   - **missed-knowledge**: the method was sound, but a fact about the environment (what a table or job argument means, a connector pattern, code ownership) or the domain (how a vendor's queue actually behaves, once their side answered) was unknown and written nowhere the command reads.
   - **missed-judgment**: the facts were right and the deliverable was wrong: mode, register, length, audience, engineering work in a draft aimed at non-technical people, an invented escalation target, process steps I had not decided on, a revision that changed more than the correction named. What I cut or rewrote before posting, and what I later had to post as a correction, both count.
5. For each confirmed miss identify the mechanism, not just the fact: which step or discipline of `/investigate-ticket` owned it, and which audit item or pre-output check should have caught it. Then decide whether the rule existed and did not bite (enforcement miss: quote the rule, and what the findings actually held against it, such as an audit item answered with an adjective where its siblings demand a named query or row) or genuinely did not exist (gap).
6. **Rank by value, cost and likelihood of happening again.** For each confirmed miss rate: value (what the miss cost when it bit: a wrong statement in a customer-facing thread or a wrong production action, versus an over-long draft I trimmed in a minute), cost (of the fix, including what it adds to every future case, and whether the existing audit or gate already catches it), and likelihood (how often the trigger recurs; count it in past session transcripts when you can). Order the findings by that, and say plainly what you would drop and why.
7. For each surviving miss, name where its fix would go: method lessons (missed-evidence, wrong-evidence, missed-judgment) to the lessons journal under the entry-level merge rule; missed-knowledge to `investigation.md` (environment) or `domain.md` (domain), in that file's house style; enforcement holes and gaps to the command (step 8). These are proposals only. Before writing an item I approved, grep the target for the mechanism and the thread: concurrent retros race.
8. Command-file edits: when a miss reveals an enforcement hole or a genuine gap in `~/.claude/commands/investigate-ticket.md`, propose the edit (line and gist) as a finding. The proposal modifies an existing step, audit item, prohibition, or gate check wherever one can carry it; a net-new rule requires showing why no existing line can. **The command lives in a public repo; the journals do not.** A proposed edit is a generic question about a mechanism, carrying no company, app, module, vendor, product, feature-flag, ticket, person, or internal URL; if a rule only makes sense with those attached, it is missed-knowledge and belongs in a journal. When an approved command edit would replace a journal entry, propose deleting that entry in the same item: the command is the binding copy, and a duplicate taxes every future case twice.
9. Never post anything to Slack and never touch production. If a posted claim of mine is wrong and still uncorrected in the thread, say so first in the report; drafting or posting the correction is `/investigate-ticket`'s job under its unlock rule, never this command's.

## Report shape

Short: one screen, no essays. I read it to decide, not to study.

1. Any posted claim of mine that is wrong and still uncorrected in the thread, one line each, or "none".
2. Counter-claims that did not hold, or held only in part: one line each with the evidence pointer.
3. The findings, ranked: a table with the finding (one line), class, value, cost, likelihood, and the proposed fix (target file and line, the gist in a few words). Dropped findings go in one line at the end, with the reason.
4. One question: which items to write.

The full claim table, the evidence, and the exact wording stay out unless I ask for them.
